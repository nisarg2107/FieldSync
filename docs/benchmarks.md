# Reproduce the synchronization checks

Run from `backend/`:

```sh
go test -cover ./...
go run ./cmd/simulate -seed 42 -replicas 3 -edits 120 -loss 0.6 -delay 2ms -out ../docs/sample-benchmark.json
go test ./internal/crdt -run '^$' -bench . -benchmem
```

The sample report is generated by that command, not a target performance promise.
`elapsedMs` and `recoveryMs` vary by host. The seeded request schedule is repeatable.
The simulator sorts map-derived pending operations before delivery; CRDT correctness
does not depend on that order.

| Metric | What is measured |
| --- | --- |
| `converged` | All task registers equal, all replicas know every unique operation, and all outboxes are empty |
| `droppedRequests` | Request rejected by the faulty link before it reaches the API |
| `lostResponses` | API processed and committed, but its response was discarded |
| `duplicateDeliveries` | Downloaded operation deliberately applied again |
| `reorderedResponses` | Download page shuffled before the reducer sees it |
| `restarts` | Client metadata, operation log, outbox, and snapshots serialized and reconstructed |
| `recoveryRequests` / `recoveryMs` | Calls/time after loss is disabled, including two passes to catch late uploads |
| `jsonPayloadBytes` | Request plus response JSON lengths for requests that reach the handler, including lost responses |
| `idleResponseBytes` | Actual response body for a caught-up client's next poll |
| `fullLogResponseBytes` | Equivalent JSON response containing all operations, without paging, for comparison |

The `loss` flag is a fault intensity: each request has `loss/2` chance of dropping
before processing, then a separate `loss/2` chance of losing its response. Thus
`-loss 0.6` does **not** mean exactly 60% packet loss. `delay` injects one delay per
attempt. These are application-level faults through Go's actual HTTP handler using
`httptest`, not real TCP packet loss or a production network benchmark. Headers,
TLS, TCP overhead, Android rendering time, and PostgreSQL latency are not included.

The Go simulation uses the in-memory store and a Go reference replica. It does not
pretend to execute Kotlin or Android. The shared fixture checks cross-language
merge behavior. Real Room tests separately reopen on-disk databases and test the
Android peer endpoint; PostgreSQL contract tests run only when `TEST_DATABASE_URL`
is present. See [validation](validation.md) for what was actually run on this host.

The fault simulator generates title/completion/archive operations. Shared collaboration
fixtures and Android integration tests separately cover checklists, photo metadata,
explicit status conflicts, team roles, and binary photo transfer. These reports are
not measurements of Nearby radio latency or photo throughput. The app's sync history
shows estimated JSON/file payload bytes; it excludes HTTP headers, SDK framing, and
radio overhead, and failed transfers can be undercounted.

`BenchmarkApply` measures the reducer only. Use it for relative local experiments,
not claims about sustained server throughput. The memory store favors readability
over indexing and is intended for tests and small demos.
